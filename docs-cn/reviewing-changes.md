# 审查变更

OpenSpec 的全部承诺是你和你的 AI **在任何代码被写之前就先就"要做什么"达成一致。**那个协议只有在你真正读了 AI 起草的内容时才有意义。本页讲的是你做这件事的那两分钟——打开什么，按什么顺序，看什么。

赌注很简单：在一段话的计划中抓住错误转向几乎是免费的。在 300 行代码中抓住同样的错误转向不是。审查是你兑现那个赌注的地方。

## 你审查的两个时刻

确有两个：

```
/opsx:propose ──► 审查计划 ──► /opsx:apply ──► 审查代码 ──► /opsx:archive
                  （任何代码之前）                    （/opsx:verify）
```

1. **在 `/opsx:propose` 之后**（或 `/opsx:ff`），在 `/opsx:apply` 之前——当计划还只是文字时读它。
2. **在构建之后**，用 `/opsx:verify`——检查代码是否真的做了计划说的。

第一个审查是为你节省最多的，也是人们跳过的。本页大部分时间在那里。

## 按这个顺序读

变更是 `openspec/changes/<name>/` 下的一个纯 Markdown 文件夹。按让你能最早发现错误就退出的顺序读文件：

```
openspec/changes/add-dark-mode/
├── proposal.md      1. 意图和范围   ← 如果这个错了，在这里停
├── specs/…/spec.md  2. 需求         ← 审查的核心
├── design.md        （仅对于更大的变更）— 技术方案
└── tasks.md         3. 工作计划
```

你不需要读每一行。你需要回答三个问题，每个文件一个。

## 提案：这是正确的问题吗？

先打开 `proposal.md`。它记录"为什么"和"是什么"——意图、范围、方案，用一两段话。

**好的样子：**一个清晰的意图，一个你认识的范围，和一个现在做这个值得的理由。

**红旗：**

- 它解决了一个与你要求的*略有不同*的问题。
- 范围长了——你要一个主题切换，提案也"趁我们在这"碰了认证。
- 它模糊。"改进设置页"不是一个范围；"添加一个尊重操作系统偏好的暗色模式切换"是。

**要回答的问题：** *这匹配我实际要求的吗，有东西溜进来了吗？*如果答案是不，停——不要继续读，修复提案（参见 [回退很便宜](#回退很便宜)）。

## 规范增量："完成"定义正确吗？

这是审查的核心。`specs/` 下的增量规范说当变更发布时什么将是*真的*——作为需求和证明它们的场景：

```markdown
## ADDED Requirements

### Requirement: 暗色模式切换
系统 SHALL 让用户能在浅色和暗色主题之间切换。

#### Scenario: 首次加载时尊重操作系统偏好
- GIVEN 一个从未设置过主题的用户
- WHEN 他们在一个设置为暗色模式的设备上打开应用
- THEN 应用以暗色模式渲染
```

**好的需求的样子：**一个清晰的 `SHALL`/`MUST` 声明你可以交给一个测试者，以及至少一个场景其 GIVEN/WHEN/THEN 真正演练了那个声明。

**红旗：**

- **模糊的需求。**"系统 SHALL 很快"不能被构建或测试。什么是快？
- **一个没有场景的需求**，或者一个不测试它所在需求下的场景。
- **最有价值的发现：缺了什么。**AI 忠实地写下你*说*的。你的工作是注意到你*忘记*说的。如果你最关心操作系统偏好案例但没有场景提到它，那就是审查在为你挣钱。

读增量，问*如果系统做了确切——且仅——这个，我会满意吗？*这里还没有关于代码的东西，所以改变它仍然便宜。

## 任务：工作计划合理吗？

最后打开 `tasks.md`。这是 AI 将按清单工作的实施检查清单。

**好的样子：**有序步骤，每个可追溯到需求，没有神秘的东西。

**红旗：**

- 一个没有匹配需求的任务（那是从哪来的？）。
- 一个巨大的"实现功能"任务隐藏了所有真正的决策。
- 一个任务触及了你刚批准的范围之外的东西。

你不在估算或微观管理——你在检查计划匹配你已经接受的需求。

## 回退很便宜

如果三个问题中任何一个错了，说出来。没有阶段，没有东西被锁定——你修复它然后继续。两种方式，和 [编辑变更](editing-changes.md) 中一样：

- **自己编辑文件。**它是纯 Markdown；改范围行，收紧需求，删除任务。
- **告诉 AI 哪里错了**让它修订：*"去掉认证相关的改动——超出范围，"* *"为用户已经选了主题的情况添加一个场景，"* *"把任务 3 拆成 schema 和 UI。"*

然后重新读你改的部分。重新起草直到它是一个你会签名的计划。那个来回*就是*产品在工作。

## 代码之后：验证

一旦工作构建完成，`/opsx:verify` 是你的第二次审查。它重新读取产出物和代码，在三个维度报告不匹配：

| 维度 | 它检查什么 |
|-----------|----------------|
| **完整性** | 每个任务完成，每个需求实现，场景覆盖 |
| **正确性** | 实现匹配规范的意图，边缘情况处理 |
| **一致性** | 设计决策实际出现在代码中 |

```
你：/opsx:verify

AI：正在验证 add-dark-mode...

     完整性
     ✓ 所有 8 个任务在 tasks.md 中检查了
     ✓ 所有规范中的需求有对应代码
     ⚠ 场景"首次加载时尊重操作系统偏好"没有测试覆盖
```

它把问题标记为 CRITICAL、WARNING 或 SUGGESTION，它**不**阻塞归档——它展示差距，把决定留给你。这是"AI 写了代码吗"和"它构建了我们同意的吗"之间的区别。

`/opsx:verify` 在扩展配置文件中。如果你没有，通过 `openspec config profile`（然后 `openspec update`）开启它，或者自己重新读变更和差异。

## 适当调整审查规模

不是每个变更都值得全流程。一个单文件错字修复值得二十秒浏览。一个触及认证、支付或你无法恢复的数据的变更值得上面每个问题。重点从来不是仪式——而是把你的注意力花在错误代价昂贵的地方，在不会的地方浏览。

## 二分钟检查清单

- [ ] 提案的意图匹配我要求的。
- [ ] 没有额外的东西溜进了范围。
- [ ] 每个需求足够具体可以被测试。
- [ ] 每个需求有一个真正演练它的场景。
- [ ] 我最关心的案例被覆盖了。
- [ ] 任务映射到需求；没有神秘或超出范围的东西。
- [ ] 如果 AI 构建了确切这个且仅此，我会舒服。

如果全部七条通过，自信地运行 `/opsx:apply`。如果任何一条失败，那不是挫折——那是两分钟在做它的工作。
