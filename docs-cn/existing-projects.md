# 在存量项目中使用 OpenSpec

**你不需要记录整个代码库才能开始。你只为你即将变更的那部分写规范。**这是关于在现有项目上采用 OpenSpec 最重要的一件事，也是为什么 OpenSpec 是存量优先构建的。

一个常见的担忧是这样的："我的应用有 80000 行旧代码。我需要先为所有代码写规范，然后 OpenSpec 才有用吗？"不需要。你会讨厌那样，我们也一样。OpenSpec 一次一个变更地增长你的规范。你的第一个变更记录它触及的那一片，下一个变更记录它的那片，几个月后，你的规范自然地围绕你实际做的工作填满。

本指南展示如何在第一天开始，不搞全盘重写。

## 三十秒版本

```bash
$ cd your-existing-project
$ openspec init          # 添加 openspec/ 和你的 AI 工具的命令
```

然后，在你的 AI 聊天中：

```text
/opsx:explore            # 可选：让 AI 阅读你将触及的领域
/opsx:propose <一个你真正需要的、小的真实变更>
/opsx:apply
/opsx:archive
```

现在你的规范精确地描述了那个变更触及的系统部分，仅此而已。这是正确的。你做完就无需担心其他 80000 行。

## 为什么增量优先是全部诀窍

OpenSpec 变更被写成**增量**：`ADDED`、`MODIFIED`、`REMOVED`。增量描述相对于当前行为发生了什么变化，而非整个系统。

这正是存量工作需要的。你很少从零开始。你在添加字段、修复重定向、收紧超时。增量让你精确地指定那个变更，而不需要先写一个 40 页的涵盖一切的规范。

所以你的 `openspec/specs/` 目录不一开始就完整。它开始几乎为空，逐渐积累。每个归档的变更将其增量合并进去。`auth/` 的规范只有在你做了几个 auth 变更后才变得全面，这恰好是你需要它全面的时候。

如果你想要更深入的机制，参见 [概念：增量规范](concepts.md#delta-specs)。

## 你在真实代码库上的第一个变更

选小而真实的东西。不是玩具，不是重写。一个你这周本来就要做的变更。小的第一个变更以低风险教会你工作流。

**步骤 1：让 AI 阅读相关区域。**这是 `/opsx:explore` 在不熟悉或大型代码库上发挥价值的地方。指向你即将触及的部分，让它在提案任何东西之前映射事物如何运作。

```text
你：/opsx:explore

AI：你想探索什么？

你：我需要为我们的公共 API 添加速率限制，但我不确定请求目前如何流经中间件。

AI：让我追踪一下…… [读取路由、中间件栈和配置]
     请求命中 Express，通过 auth 中间件，然后是你控制器。
     目前没有速率限制层。最干净的插入点是 auth 之后的一个中间件。想要我划定范围吗？
```

注意 AI 现在理解了你的实际结构，所以它写的提案将适配你的代码，而非一个通用模板。在大型代码库上，这个单一习惯节省最多痛苦。参见 [探索优先](explore.md)。

**步骤 2：提案变更。**提案和其增量规范仅捕获这个变更。

```text
你：/opsx:propose add-api-rate-limiting
```

**步骤 3：构建和归档**，用 `/opsx:apply` 和 `/opsx:archive`，和其他变更一样。归档后，你为你的速率限制行为有了一个真实的规范，诞生于一个你本来就需要做的变更。

## 更喜欢引导式旅程？使用 onboard

如果你想在你的代码上观看整个循环并带着讲解，扩展命令 `/opsx:onboard` 正是做这个：它扫描你的代码库寻找一个小而安全的改进，然后带你走完提案、构建和归档，解释每一步。

先开启扩展命令：

```bash
$ openspec config profile      # 选择扩展工作流
$ openspec update              # 将它们应用到本项目
```

然后在聊天中：

```text
/opsx:onboard
```

它是在真实项目上最温和的介绍，它留给你一个真实的（小）变更，你可以保留或丢弃。参见 [命令：`/opsx:onboard`](commands.md#opsxonboard)。

## "但我已经有需求文档"

也许你有 PRD、SRS、正式规范，甚至 TLA+ 模型。很好。你不要整体导入它们，但也不要扔掉它们。

把现有文档视为**探索的源材料**，而非要转换的规范。当你开始一个变更时，粘贴或指向 AI 相关章节，让它从中塑造一个聚焦的 OpenSpec 增量。增量以 OpenSpec 的可测试需求与场景形式捕获你当下正在变更的行为。你原始的文档保持原样作为背景。

诚实的原因：OpenSpec 规范是故意行为优先且范围限定于变更的。一个 40 页的 PRD 是一个不同目的的不同产出物。强制一次性批量转换倾向于产生大量陈旧、没人信任的规范。让规范从真实变更中生长保持它们准确。

```text
你：/opsx:explore
你：这是我们 PRD 中关于结账的部分。我接下来要实现"访客结账"需求。
     [粘贴相关需求]
AI：[读取它，问澄清问题，然后帮助划定变更范围]
你：/opsx:propose add-guest-checkout
```

## 在大型代码库中组织规范

规范位于 `openspec/specs/` 下，按**领域**分组：一个匹配你团队如何思考系统的逻辑区域。你不需要预先设计整个分类法。当你在该领域的第一个变更需要一个领域文件夹时创建它。

常见的领域划分方式：

- **按功能区域：** `auth/`、`payments/`、`search/`
- **按组件：** `api/`、`frontend/`、`workers/`
- **按限定上下文：** `ordering/`、`fulfillment/`、`inventory/`

选任何让新人一眼看懂的。你可以之后细化。参见 [概念：规范](concepts.md#specs)。

## 单一仓库和跨仓库工作

对于单一仓库，最简单的模型是仓库根目录下一个 `openspec/` 目录，领域映射到你的包或服务。这对大多数团队足够了。

如果你的工作真正跨越**多个仓库**（或几个你视为独立的包），OpenSpec 有一个 beta 的 **stores** 功能：规划生活在自己的独立仓库中，你的任何代码仓库都可以引用，所以计划不必住在某个仓库的 `openspec/` 文件夹内。它是 beta，所以它命令和状态可能会变化。从 [Stores 用户指南](stores-beta/user-guide.md) 开始了解心智模型和最小可用路径。

## 几个诚实的提醒

- **抵制回填一切的冲动。**为你不正在变更的代码写规范感觉有生产力，但通常不是。那些规范会变陈旧，因为没有东西强迫它们跟踪现实。让真实变更驱动你的规范。
- **保持早期变更小。**你前几个变更既是学习节奏也是交付。紧凑的范围让循环快、教训便宜。
- **将 `openspec/` 提交到 git。**你的规范和归档属于版本控制，和它们描述的代码一起。
- **给 AI 上下文。**在有强约定的大型代码库上，填写 `openspec/config.yaml` 的 `context:` 以便每个提案尊重你的技术栈和模式。参见 [自定义](customization.md#project-configuration)。
