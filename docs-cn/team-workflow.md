# 团队中的 OpenSpec

其他指南中的所有内容无论你是独自一人还是二十人团队都一样工作。团队中变化的是边缘问题：规范放在哪里，队友如何审查计划，以及这些如何适配我们已有的 PR 流程？

简短答案：变更是文件，OpenSpec 从不碰 git。所以它适配你现有的工作流而非替代它。本页讲述运行良好的约定。

## 一条规则：OpenSpec 不碰 git

OpenSpec 在 `openspec/` 下读写纯 Markdown。它从不提交、分支、推送或拉取你的项目——也从不自己克隆或同步 [store](stores-beta/user-guide.md)。这意味着：

- **你像任何源码一样提交 `openspec/`。**规范、活跃变更和归档是你项目历史的一部分。（是的，提交整个文件夹——参见 [FAQ](faq.md#should-i-commit-the-openspec-folder-to-git)。）
- **变更是你像代码一样版本控制的文件夹。**`openspec/changes/add-dark-mode/` 只是分支上的文件。
- **以下一切都是约定，并非强制。**OpenSpec 不会强迫你这样做；它只是适配得很干净。

## 日常循环

运行良好的工作流将一个变更映射到一个分支和一个 PR：

```
git switch -c add-dark-mode        开始一个分支，照常
   │
/opsx:propose add-dark-mode        起草计划（proposal + specs + tasks）
   │
审查计划                            你在任何代码之前读它——参见 审查变更
   │
/opsx:apply                        构建；产出物 + 代码一起变化
   │
git commit && 打开 PR              PR 包含增量规范 AND 代码
   │
队友审查，合并
   │
/opsx:archive                      将增量折叠进 specs/，将变更移到 archive/
```

计划和代码在同一分支上共存，所以你的队友一起审查两者，六个月后归档的规范仍然解释为什么代码是那个样子。

## 在 PR 中审查规范

这是团队感受回报的地方。当 PR 包含变更的增量规范时，审查者得到原始差异从不给的东西：**一个平实语言的声明，说明这个变更应该做什么**，在他们读任何一行代码之前。

给审查者的好审查顺序：

1. **读 `proposal.md`**——这是正确的问题和范围吗？
2. **读 `specs/` 下的增量**——"完成"定义正确吗？（这是 [审查变更](reviewing-changes.md) 的二分钟审查法，现在发生在 PR 中。）
3. **然后读代码差异**——它交付了确切那些需求吗？

不同意*方案*的审查者可以针对提案表达，便宜地，而不是在 300 行代码上重新争论。把增量规范放在 PR 描述顶部，或指向变更文件夹给审查者，让他们从那里开始。

## 何时归档

归档将变更的增量折叠进你的主 `openspec/specs/` 并将变更文件夹移到 `openspec/changes/archive/YYYY-MM-DD-<name>/`。因为 `specs/` 是**共享的真理之源**，时机在团队中很重要。两个可行的约定：

- **PR 合并后归档（推荐）。**分支携带活跃变更；一旦它合并到你的主分支，在那里归档（通常是一个微小的后续提交或定期清理）。这保持共享的 `specs/` 只与实际交付的工作一起前进。
- **在 PR 内归档。**对小团队更简单：添加代码的同一个 PR 也同步和归档。代价是你的 `specs/` 差异和代码差异一起落地，可能使 PR 更嘈杂。

选一个并保持一致。无论哪种方式，`/opsx:archive` 检查任务是否完成并提供先同步，所以没有东西意外地半完成合并。

## 两个人，并行变更

因为变更是单独的文件夹，它们不碰撞：

- **不同变更，不同人——没问题。** `add-dark-mode` 和 `rate-limit-login` 是不同分支上的不同文件夹；它们从不互相触碰直到它们都归档。
- **一个变更，一个拥有者。**两个人编辑同一个变更文件夹冲突，就像两个人编辑同一个文件。保持变更给单一作者，或拆成两个变更（另一个适当调整规模的理由——参见 [撰写好的规范](writing-specs.md#right-size-the-change)）。
- **冲突出现的唯一地方是 `specs/`。**如果两个变更都修改*同一个*需求，归档第二个将在 `openspec/specs/…/spec.md` 中冲突——像任何合并冲突一样解决，保留反映现实的需求。这很少见，是一个特性：是 git 告诉你两个变更对系统应该如何行为意见不一致。

## 当规划超出单个仓库

以上所有假设计划住在代码仓库自己的 `openspec/` 文件夹中，这是正确的默认。当你的规划真正跨越多个仓库或团队——一个功能涉及三个服务，或需求由一个团队拥有、其他团队消费——这就是 beta **stores** 功能的用途：规划获得自己的仓库，任何代码仓库都可以指向它。从 [Stores 用户指南](stores-beta/user-guide.md) 开始。
