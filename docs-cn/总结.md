# OpenSpec 项目架构分析

## 一、项目是做什么的

**OpenSpec** 是一个 **AI 原生的规范驱动开发系统**（AI-native system for spec-driven development）。

一句话定位：**让人和 AI 在写代码之前先就"要做什么"达成一致。**

它的核心理念来自 [README.md](file:///d:/AndroidStudioProjects/github_space/OpenSpec/README.md)：

```
→ fluid not rigid         流畅而非死板
→ iterative not waterfall  迭代而非瀑布
→ easy not complex         简单而非复杂
→ built for brownfield     适配存量代码库，而非仅面向新项目
→ scalable                 从个人项目到企业都能用
```

**它解决了什么痛点**：AI 写代码很强，但需求如果只活在聊天记录里，AI 就会"自信地写错"。OpenSpec 给项目加一层薄薄的规范层，让"做什么"在写代码前先达成共识。

**典型工作流**（来自 `docs/overview.md`）：

```
/opsx:explore   (可选) AI 先陪你梳理思路
/opsx:propose   AI 一次性起草 proposal + specs + design + tasks
                (你阅读并调整)
/opsx:apply     AI 按 tasks 实施代码
/opsx:archive   把变更归档，specs 合并进主规范
```

**两种命令各司其职**（来自 `docs/how-commands-work.md`）：

- `openspec ...` 跑在**终端**（如 `openspec init`、`openspec list`、`openspec view`）
- `/opsx:...` 跑在 **AI 助手的聊天框**里（如 `/opsx:propose`、`/opsx:apply`）

## 三、整体架构设计

OpenSpec 的架构是一套 **"双层 + 引擎/方向盘"** 设计，可以画成下面这张图：

```

                         │              用户/开发者                  │

                                      ▼                 ▼
        ┌──────────────────────────────────┐   ┌──────────────────────────────┐
        │  $ openspec init/list/view/archive│   │  /opsx:propose /opsx:apply   │
        │      (Commander.js)              │   │  /opsx:archive /opsx:explore │
        │           │                      │   │     （在你用的 AI 工具里）    │
        │           ▼                      │   └──────────────┬───────────────┘
```

### 架构的关键设计点

**1. 引擎 / 方向盘分离（核心架构决策）**

- **CLI 是引擎**（`src/cli/index.ts`）：知道规范长什么样、artifact 怎么依赖、delta 怎么合并。所有工具共用同一个引擎。
- **斜杠命令是方向盘**：每个 AI 工具格式不同，靠 `src/core/commandGeneration/adapters/` 下的 25+ 适配器生成对应格式的 skill/command 文件。
- 这让 OpenSpec 能支持 25+ AI 工具（Claude / Cursor / Windsurf / Copilot / Codex / Trae …），而用户只学一次工作流。

**2. Schema 驱动的工作流（DNA 设计）**

- `schemas/spec-driven/schema.yaml` 用 YAML 声明 artifact 的依赖图：`proposal → specs → design → tasks → apply`。
- `src/core/artifact-graph/` 把这个声明变成可计算的 DAG：能告诉你下一个能做哪个 artifact、哪个被阻塞。
- 这是 OpenSpec "fluid not rigid" 哲学的实现基础 —— 依赖是 enabler 而非 gate。

**3. Specs / Changes 双文件夹模型**

- `openspec/specs/` 是真理之源（描述系统当前行为）。
- `openspec/changes/<change>/` 是提案（含 `proposal.md`、`specs/` delta、`design.md`、`tasks.md`、`.openspec.yaml`）。
- `archive` 时把 delta 合并回 specs，change 移入 `changes/archive/<日期-名字>/`。
- **Delta 思想**是 OpenSpec 适配存量项目的关键：你只描述"改了什么"，不需要重写整个 spec。

**4. Agent Contract（机器可读契约）**

- `docs/agent-contract.md` 规定每个 `--json` 命令的输出 schema。
- AI 工具通过 `openspec status --json`、`openspec instructions <artifact> --json` 等机器可读接口和引擎对话，而不是靠模糊的 prompt 解析。
- 这把"AI 怎么知道下一步干啥"从 prompt 工程变成了稳定的 JSON 契约。

**5. Dogfooding（自举）**

- `openspec/` 目录就是 OpenSpec 用 OpenSpec 管理自己的实例 —— 你能看到 50+ 历史变更和 36 个 capability spec。
- 这既是开发实践，也是给用户的活样本（README 明说："OpenSpec is built with OpenSpec"）。

**6. 技术栈选型**

- **TypeScript ESM + Node.js ≥ 20.19**：跨平台、AI 工具生态友好。
- **Commander.js**：CLI 框架。
- **Zod**：spec/change 元数据的 schema 校验。
- **fast-glob**：处理 `specs/**/*.md` 这类 glob。
- **@inquirer/prompts + ora + chalk**：交互式 CLI 体验。
- **Vitest**：测试（约 100 个测试文件，包括 cli-e2e 端到端）。
- **Changesets**：发版管理。
- **PostHog**：匿名遥测（可关闭）。

### 设计哲学小结

OpenSpec 的整个架构都围绕一句话：**agree first, then build confidently**（先达成共识，再自信地构建）。它通过"两文件夹 + Delta + Schema 驱动的 artifact 图 + 引擎/方向盘分离"这四个设计，把"和 AI 协作写代码"这件事从聊天记录里抽出来，变成可审查、可归档、可跨工具、可跨仓库的工作流。
