# 概念

本指南解释 OpenSpec 背后的核心思想以及它们如何组合在一起。实际使用参见 [快速上手](getting-started.md) 和 [工作流](workflows.md)。

## 哲学

OpenSpec 围绕四个原则构建：

```
fluid not rigid         — 无阶段关卡，在合理的时候做合理的事
iterative not waterfall — 边构建边学习，边做边细化
easy not complex        — 轻量设置，最小仪式
brownfield-first        — 与现有代码库一起工作，不仅仅是新项目
```

### 为什么这些原则重要

**流动而非死板。**传统规范系统把你锁在阶段里：先规划，然后实施，然后完成。OpenSpec 更灵活——你可以以对工作合理的任何顺序创建产出物。

**迭代而非瀑布。**需求变化。理解加深。开始时看起来好的方法在你看过代码库后可能不成立。OpenSpec 拥抱这个现实。

**简单而非复杂。**一些规范框架需要大量设置、刚性格式或重量级流程。OpenSpec 不碍事。几秒初始化，立即开始工作，只在需要时自定义。

**存量优先。**大多数软件工作不是从零开始——是修改现有系统。OpenSpec 基于增量的方法使得指定对现有行为的变更很容易，不仅仅是描述新系统。

## 全局图

OpenSpec 将你的工作组织成两个主要区域：

```
┌────────────────────────────────────────────────────────────────────┐
│                        openspec/                                   │
│                                                                    │
│   ┌─────────────────────┐      ┌───────────────────────────────┐   │
│   │       specs/        │      │         changes/              │   │
│   │                     │      │                               │   │
│   │  真理之源            │◄─────│  提案的修改                    │   │
│   │  你的系统当前        │ 合并 │  每个变更 = 一个文件夹         │   │
│   │  如何运作            │      │  包含产出物 + 增量             │   │
│   │                     │      │                               │   │
│   └─────────────────────┘      └───────────────────────────────┘   │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**规范**是真理之源——它们描述你的系统当前如何行为。

**变更**是提案的修改——它们存在于单独的文件夹中，直到你准备好合并它们。

这个分离是关键。你可以并行处理多个变更而不冲突。你可以在变更影响主规范之前审查它。当你归档一个变更时，其增量干净地合并到真理之源。

## 规范

规范使用结构化需求和场景描述你的系统行为。

### 结构

```
openspec/specs/
├── auth/
│   └── spec.md           # 认证行为
├── payments/
│   └── spec.md           # 支付处理
├── notifications/
│   └── spec.md           # 通知系统
└── ui/
    └── spec.md           # UI 行为和主题
```

按领域组织规范——匹配你团队如何思考系统的逻辑分组。

### 规范格式

一个规范包含需求，每个需求有场景：

```markdown
# Auth 规范

## 目的
应用的认证和会话管理。

## 需求

### Requirement: 用户认证
系统 SHALL 在成功登录后颁发 JWT 令牌。

#### Scenario: 有效凭据
- GIVEN 一个有有效凭据的用户
- WHEN 用户提交登录表单
- THEN 返回一个 JWT 令牌
- AND 用户被重定向到仪表板

#### Scenario: 无效凭据
- GIVEN 无效凭据
- WHEN 用户提交登录表单
- THEN 显示错误消息
- AND 不颁发令牌
```

### 规范是什么（不是）

规范是一个**行为协议**，不是实施计划。

好的规范内容：
- 用户或下游系统依赖的可观察行为
- 输入、输出和错误条件
- 外部约束（安全、隐私、可靠性、兼容性）
- 可以测试或显式验证的场景

规范中避免：
- 内部类/函数名
- 库或框架选择
- 逐步实施细节
- 详细执行计划（那些属于 `design.md` 或 `tasks.md`）

快速测试：如果实现可以改变而不改变外部可见行为，它可能不属于规范。

### 保持轻量：渐进严谨

OpenSpec 旨在避免官僚主义。使用仍然使变更可验证的最轻量级别。

**精简规范（默认）：**
- 简短的行为优先需求
- 清晰的范围和非目标
- 几个具体的验收检查

**完整规范（用于高风险）：**
- 跨团队或跨仓库变更
- API/协议变更、迁移、安全/隐私问题
- 模糊性可能导致昂贵返工的变更

大多数变更应保持在精简模式。

### 人与 Agent 协作

在许多团队中，人类探索，agent 起草产出物。预期循环是：

1. 人类提供意图、上下文和约束。
2. Agent 将其转换为行为优先的需求和场景。
3. Agent 将实施细节放在 `design.md` 和 `tasks.md` 中，而非 `spec.md`。
4. 验证在实施前确认结构和清晰度。

## 变更

变更是对你系统的提案修改，打包为一个文件夹，包含理解和实施它所需的一切。

### 变更结构

```
openspec/changes/add-dark-mode/
├── proposal.md           # 为什么和是什么
├── design.md             # 怎么做（技术方案）
├── tasks.md              # 实施检查清单
├── .openspec.yaml        # 变更元数据（可选）：schema, created, skip_specs
└── specs/                # 增量规范
    └── ui/
        └── spec.md       # ui/spec.md 中什么在变
```

## 增量规范

增量规范是 OpenSpec 中的核心概念。它们展示相对于你当前规范发生了什么变化。

### 增量操作

- **`## ADDED Requirements`** — 新能力
- **`## MODIFIED Requirements`** — 变更的行为 — 必须包含完整更新内容
- **`## REMOVED Requirements`** — 废弃功能 — 必须包含**原因**和**迁移**
- **`## RENAMED Requirements`** — 仅名称变更 — 使用 FROM:/TO: 格式

### 归档时发生什么

归档一个变更时：

1. **ADDED** 需求被追加到主规范
2. **MODIFIED** 需求替换现有版本
3. **REMOVED** 需求从主规范中删除

变更文件夹移动到 `openspec/changes/archive/` 用于审计历史。

## 产出物和依赖图

Artifact 形成有向图。依赖是赋能者，而非守门员：

```
                        proposal
                       （根节点）
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
           specs                       design
        （需要：                     （需要：
         proposal）                   proposal）
              │                           │
              └─────────────┬─────────────┘
                            │
                            ▼
                         tasks
                     （需要：
                     specs, design）
```

当你运行 `/opsx:continue`，它检查什么就绪并提供下一个产出物。你也可以按任意顺序创建多个就绪的产出物。

## 产出物

| 产出物 | 用途 |
|----------|---------|
| `proposal.md` | "为什么"和"是什么"——记录意图、范围和方案 |
| `specs/` | 增量规范，展示 ADDED/MODIFIED/REMOVED 的需求 |
| `design.md` | "怎么做"——技术方案和架构决策 |
| `tasks.md` | 实施检查清单，带复选框 |

## 配置

### 项目配置（config.yaml）

```yaml
schema: spec-driven

context: |
  你的项目背景、技术栈、约定和约束。

rules:
  proposal:
    - 包含回滚计划
  specs:
    - 使用 Given/When/Then 格式
  design:
    - 记录回退策略
  tasks:
    - 拆分为最大 2 小时的块
```

### Schema 解析

当确定使用哪个 schema 时，按顺序检查：

1. CLI 标志：`--schema <name>`（最高优先级）
2. 变更元数据：变更目录中的 `.openspec.yaml`
3. 项目配置：`openspec/config.yaml`
4. 默认：`spec-driven`

## 归档

归档完成变更。其增量规范合并到主规范，变更文件夹移到 `openspec/changes/archive/YYYY-MM-DD-<name>/`。归档后，你的规范描述新的现实。

## 通过 OPSX 自定义

OPSX 是 OpenSpec 的流动工作流。它使用外部 schema 和依赖图引擎，而非硬编码模板。
